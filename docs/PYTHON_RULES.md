# Python 开发规则

## 依据与适用范围

本项目采用用户指定的 [Google Python 风格规范（中文版）](https://zh-google-styleguide.readthedocs.io/en/latest/google-python-styleguide/python_style_rules.html)，于 2026-11-16 建立本地执行规则。该页面是规范依据；本文将其转化为项目开发约束，未展开的细节及例外须查阅原文对应章节。以下明确标注的“项目约定”用于统一原文允许的选择或补充执行流程。

- 适用于本仓库后续新增、生成、复制引入及实际修改的 Python 代码，包括业务模块、测试、工具脚本、迁移和示例。
- 已有且本次未修改的代码暂不整改。修改范围内遵守规范，避免全文件格式化造成无关差异。
- 保留已有公共接口和第三方框架要求的名称、签名；确需保留不符合风格的接口时，在变更说明中记录兼容原因，新增内部实现遵守本规范。
- Python 版本以项目打包配置为准。编写代码前检查最低支持版本，不因本机版本较新就采用不兼容的语法或标准库 API。
- 原文里的历史示例仅用于说明风格，不照搬过时语法、Google 内部工具或依赖。

## 排版

- 每级缩进使用 4 个空格，不使用 Tab；续行使用括号内对齐或增加 4 个空格的悬挂缩进。
- 默认行宽为 80 个字符。原文允许的长导入、注释中的 URL/路径/长标志、不宜拆分的无空格模块级字符串常量、Pylint 禁用注释可以超出；格式化工具无法合理拆分时，先尝试手工调整，再保留必要例外。
- 使用圆括号、方括号、花括号隐式续行，不使用反斜杠续接代码。条件和返回表达式不加无意义的外围括号。
- 不添加行尾分号，不用分号连接语句。项目约定：条件分支和循环的主体另起一行，即使单行写法合法。
- 多行参数或容器的闭括号独占一行时，最后一项保留尾逗号；闭括号与起始语句的缩进对齐。单元素元组保留必要逗号。
- 项目约定：顶层定义间空两行，类的方法间空一行；去除行尾空白，文件末尾保留换行。
- 项目约定：运算符两侧及逗号后保留正常空格，不以空格列对齐赋值。无类型注解的默认参数和调用关键字使用 `name=value`；带注解的默认参数使用 `name: Type = value`。

## 导入与模块

- 导入放在模块文档字符串之后、模块级变量和常量之前；依次组织 `__future__`、标准库、第三方库、仓库内模块。
- 各组按完整模块路径排序，忽略大小写。项目约定：组间空一行，仓库内模块不再按“同子包/其他子包”拆组。
- 每条导入独占一行，不写 `import os, sys`。`typing` 和 `collections.abc` 可在一条 `from` 导入中列出多个名称。
- 项目约定：使用显式导入，避免通配符；优先导入模块，以模块名限定调用来源。框架 API 和类型名称需要直接导入时保持清晰、无歧义。
- 可执行模块将主要流程放进 `main()`，通过 `if __name__ == "__main__":` 调用；导入模块不能启动服务、执行任务或触发业务网络请求。
- 仅需要在类 Unix 环境直接执行的入口脚本添加合适的 Python 3 shebang；普通模块无需添加。
- 新文件保留项目实际适用的许可证声明，遵循仓库 LICENSE，不能凭空指定版权人或更换许可。

## 命名与结构

- 包、模块、函数、方法、参数和变量使用描述性的 `snake_case`；类、异常和类型别名使用 `CapWords`；常量使用 `UPPER_SNAKE_CASE`。
- Python 文件使用 `.py` 后缀，文件名和包名不用连字符。内部成员优先用单个前导下划线，避免无必要的双下划线名称改写；不自创 Python 保留的双端双下划线名称。
- 避免含糊缩写、无意义的类型后缀和难以理解的单字母名。局部计数器等原文允许的短名可用；数学算法使用短符号时记录符号来源或含义，公开 API 仍使用描述性名称。
- 测试名称采用 `test_<行为或方法>_<场景>`，使失败时能识别被验证的行为。
- 函数保持单一职责；超过约 40 行时评估拆分，行数不是机械限制。将相关函数和类放在同一模块，不要求每个类单独建文件。
- 简单数据优先用属性，简单计算可用 property；有明显成本或副作用的读写使用明确的方法，不为普通属性机械添加 getter/setter。

## 注释与文档字符串

- docstring 使用三重双引号，先写带句末标点的单行摘要；需要详细说明时，摘要后空一行。
- 普通模块描述职责及必要用法；测试模块仅在有额外环境、初始化或运行要求时添加模块 docstring。
- 类描述实例代表的事物；公开属性需要说明时写 `Attributes:`。公开函数、复杂或较长的函数必须提供足够的调用说明，包括对调用者有影响的副作用。
- 项目约定：使用 Google 风格英文小节名 `Args:`、`Returns:`、`Yields:`、`Raises:`、`Attributes:`，小节内容缩进 4 个空格。正文可用中文或英文，同一文件保持一致。
- 参数说明覆盖需解释的参数，包括 `*args`、`**kwargs`；未注解的类型在文档中说明。只返回 `None` 时省略 `Returns:`，生成器用 `Yields:`；元组返回值作为一个整体说明。
- `Raises:` 记录接口约定的异常，不把误用接口造成的所有偶然异常都写成承诺。签名和单行摘要足够清晰时，无需堆砌空洞的小节。
- 覆写方法可引用基类说明，但新增行为、约束或副作用必须补充记录。property 的摘要描述属性含义。
- 注释解释业务意图、约束和不明显的原因，不复述语句；行尾注释与代码至少间隔两空格，`#` 后至少一个空格。
- 临时方案用 `TODO(真实议题链接或负责人): 具体事项`，涉及未来处理时写明触发条件或日期；不编造链接、负责人或空泛承诺。

## 字符串、日志与资源

- 一般文本格式化使用 f-string、`format` 或 `%`，不靠多段 `+` 拼接格式；循环聚合文本使用 `join` 或 `io.StringIO`。
- 文件内普通字符串引号保持一致；项目约定：新文件默认双引号，修改旧文件延续原有选择，减少转义时可以改用另一种引号。docstring 始终用三重双引号。
- 对接受 `%` 模板及独立参数的日志 API，传入固定模板和独立值，例如 `logger.info("Loaded %d records", count)`，不用 f-string 或预先插值。
- 错误消息准确描述真实失败条件，动态值与描述清晰分隔，保留稳定、可搜索的文字；不能把失败原因猜测当成事实。
- 文件、套接字、数据库连接等有状态资源及时释放，优先使用上下文管理器；适用时使用 `contextlib.closing()`。无法用上下文管理时明确释放责任和时机，不依赖垃圾回收隐式清理。

## 类型注解

- 公开 API 必须注解参数和返回值；复杂、易发生类型错误的内部代码也应注解。局部类型可清晰推导时无需重复标注。
- 项目约定：新增函数在类型已确定时补全签名，`__init__` 显式标注 `-> None`；常规 `self`、`cls` 不重复标注。
- 可空值显式使用 `T | None`（在支持该语法的版本中），不能用 `value: T = None` 隐含可空性。
- 使用支持版本下的内建容器泛型，区分 `tuple[T, ...]` 与固定位置的异构元组；输入只要求迭代或映射能力时采用相应抽象类型，不无故限定具体容器。
- 复杂类型可提取语义明确的类型别名；需要泛型时使用类型变量，不用 `Any` 掩盖已知类型。确实允许任意类型的边界可以用 `Any`。
- 前向引用采用字符串注解或 `from __future__ import annotations`；涉及运行时反射的框架时确认延迟注解兼容。
- 仅用于静态检查的导入可放进 `TYPE_CHECKING` 分支；运行时实际需要的名称仍须可用。循环依赖优先调整模块边界。
- 项目约定：类型忽略或 lint 豁免限定到必要位置和具体规则，并说明原因；不能为了通过检查全局禁用规范。

## Codex 执行与交付检查

1. 开始 Python 工作前，读取本文件、目标目录的额外指令及项目版本/检查配置；不确定的规范细节查阅上方原文对应章节。
2. 编写时落实上述规则。旧文件以差异范围为边界，兼容性所需的额外修改控制在必要范围。
3. 交付前逐项检查新增或修改代码的排版、导入、命名、文档、类型、日志、资源释放和入口副作用；不能用“旧代码也是这样”解释新代码违规。
4. 运行与本次行为变更相关的现有测试和已配置检查。若已有 lint/类型工具，区分本次引入的问题与历史问题；修复本次引入的问题，不要求本次清偿历史风格问题。
5. 未配置自动检查时仍须人工核对规则；格式化通过不代表文档语义、命名、资源管理等要求都满足。报告实际验证结果及未运行检查的原因，不声称未执行的检查已通过。
6. 采用原文允许的例外或兼容性例外时，在代码附近或交付说明中记录具体原因。新增更深层规则时不得无故放宽本规范。

本次规则落地仅建立 Codex 项目指令，不自动安装 lint 工具、启用 CI 门禁或批量格式化历史代码。
